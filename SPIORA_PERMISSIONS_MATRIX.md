# SPIORA PERMISSIONS MATRIX

## Принципы

- `owner` — полный доступ и критичные административные операции.
- `manager` — рабочий доступ к бизнес-процессам без security-critical настроек.
- `consultant` — доступ только к назначенным сущностям и собственному контексту.
- `viewer` — read-only доступ там, где он вообще допустим.

Матрица ниже фиксирует целевую модель для переноса в Supabase Auth и RLS. Текущий runtime пока реализует только `owner` и `manager`.

## Матрица

| Module | Owner | Manager | Consultant |
| --- | --- | --- | --- |
| CRM | Полный доступ: читать, создавать, редактировать, архивировать | Читать, создавать, редактировать; без жёстких admin-операций | Читать только назначенных клиентов; создавать заметки/комментарии по своим клиентам |
| Calendar | Полный доступ ко всем событиям и company schedule | Читать все company events; редактировать свои и созданные им события | Читать только свои события и встречи, где он участник; редактировать только свои personal events |
| Notes | Читать/создавать/редактировать/архивировать | Читать/создавать/редактировать/архивировать | Читать и писать только по назначенным клиентам / своим задачам |
| Documents | Полный доступ, включая архивирование | Читать/создавать/редактировать; без archive/delete critical operations | Читать документы назначенных клиентов, загружать рабочие файлы в своём контуре |
| AI | Полный доступ к AI workspace, журналам и лимитам | Рабочий доступ к AI workspace | Ограниченный рабочий доступ только к разрешённым AI-инструментам |
| Analytics | Полный доступ | Нет доступа к owner-only аналитике | Нет доступа |
| Settings | Полный доступ | Нет доступа к security и системным настройкам | Нет доступа |
| Knowledge Base | Полный доступ | Читать | Читать |
| Users | Полный доступ к списку, ролям, status, reset/access governance | Читать список команды; без role/security mutation | Нет доступа или только self-profile в будущем |

## Дополнение для `viewer`

Роль `viewer` не активна в текущем runtime, но рекомендуется для будущего production:

- CRM: только чтение разрешённых записей
- Calendar: только чтение разрешённых событий
- Notes: чтение только явно разрешённых заметок
- Documents: чтение только явно разрешённых документов
- AI: нет доступа
- Analytics: по решению owner, лучше read-only curated dashboard
- Settings: нет доступа
- Knowledge Base: чтение
- Users: нет доступа

## Связь с текущим кодом

Текущая реализация подтверждает:

- owner-only разделы: `/analytics`, `/settings`
- owner-only API: `GET /api/system/health`, `/api/settings/passwords`, `/api/analytics/*`
- clients: owner/manager могут создавать и редактировать, архивировать может только owner
- notes/documents: чтение шире, write/archive уже частично ограничены ролями
- tasks: доступ строится не только по роли, но и по авторству/назначению
- calendar: доступ строится по scope, creator/owner и участию во встрече

## Что ещё нужно для production

- вынести permissions в единый RBAC registry вместо точечных inline-проверок;
- добавить отдельные capability keys, например `clients.read`, `users.manage`, `analytics.read`;
- связать capabilities с JWT claims или user-role lookup из таблицы `users`;
- дублировать критичные проверки на уровне PostgreSQL RLS.
